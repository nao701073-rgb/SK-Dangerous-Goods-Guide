# Part 507 正式運用準備 第1段階

## 対象

サーバー側認証、中央保存、権限制御を正式運用へ移行できる状態にするための実装です。

## 実装内容

1. PostgreSQLにサーバーセッションを保存します。
2. 認証情報はHttpOnly Cookieで送信し、JavaScriptから読み取れないようにします。
3. 本番環境ではSecure Cookie、HTTPS、許可Origin限定のCORSを必須とします。
4. POST・PUT・PATCH・DELETEはCSRFトークンを検証します。
5. セッションにはアイドル期限、絶対期限、強制失効、利用者単位の最大同時数を設定します。
6. 申請番号、写真、添付資料、申請書確認結果、固縛力参考算出結果は、APIで役割と所属事業所を確認してから保存・取得します。
7. ゲストには業務データの閲覧・登録権限を付与しません。
8. 永続ファイルシステムまたはS3互換ストレージの保存・読込・削除を管理画面から診断できます。
9. ログイン成功・失敗、ロック、ログアウト、更新、削除を監査履歴へ記録します。

## 適用手順

1. Part 506再構築版を適用済みのフォルダを複製して保管します。
2. Part 507更新ZIPをフォルダ構成のまま上書きします。
3. `server/.env.example`を参考に本番用環境変数を設定します。
4. `server`で`npm install`を実行します。
5. `npm run migrate`を実行し、`095_part507_server_auth_persistence_authorization.sql`まで適用します。
6. APIを再起動します。
7. Web画面のサーバー接続先をAPIのHTTPS URLへ設定します。
8. システム管理者でログインし、「設定 → セキュリティ・監査管理 → 正式運用準備 第1段階」を実行します。

## 完了条件

コードの適用だけでは第1段階の完了とはしません。導入先環境で次を確認してください。

- PostgreSQLへ登録したデータがAPI・DB再起動後も保持される。
- 写真・添付資料が再起動後も取得でき、SHA-256照合に成功する。
- 川崎事業所利用者が他事業所の案件・写真・資料を取得または変更できない。
- ゲストが申請番号管理のURL・APIを直接指定しても拒否される。
- 強制ログアウト後に、既存Cookieや旧トークンでAPIを利用できない。
- HTTPS以外の接続、許可されていないOriginからの接続が拒否される。
- 更新系APIでCSRFトークンがない場合に拒否される。

## 未実施事項

本成果物の作成環境には、導入先のPostgreSQL、永続ストレージ、正式ドメイン、TLS証明書がありません。そのため、実環境での接続・再起動後保持・事業所間権限分離試験は未実施です。これらはIT室が用意する環境で実施する必要があります。
