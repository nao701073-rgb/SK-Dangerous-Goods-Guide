# 安全環境室長へのシステム管理者権限移行仕様

## 1. 基本方針
将来のシステム管理者権限の正式な移行先は、安全環境室長に限定する。安全環境室職員、事業所管理者、一般利用者その他の役割には移行できない。

## 2. 移行段階
1. 準備：安全環境室長の本人専用アカウント、MFA、連絡先を登録する。
2. 教育：利用者管理、法令更新、監査、バックアップ、障害対応を教育する。
3. 並行運用：現行管理者の監督下で管理操作を実施する。
4. 承認：職制上の承認者、承認日、正式移行日を記録する。
5. 正式移行：再認証とMFA後、安全環境室長へシステム管理者権限を付与する。
6. 移行後確認：旧管理者を一定期間、移行支援管理者として残す。
7. 完了：監査結果と運用状況を確認し、旧管理者の通常管理権限を解除する。

## 3. 必須制御
- 移行対象者の現在の役割が `safety-environment-director` であること。
- 有効な安全環境室長アカウントが1名だけであること。
- MFAが有効であること。
- 現行管理者の再認証を行うこと。
- 職制承認記録が登録されていること。
- 移行前バックアップが完了していること。
- 権限変更前後を監査ログへ記録すること。
- 復旧用管理者アカウントを通常利用から分離すること。

## 4. 禁止事項
- 安全環境室職員への直接移行。
- 共通アカウントへの移行。
- 承認記録、MFAまたは監査ログを省略した移行。
- 旧管理者を直ちに削除し、復旧経路を失うこと。

## 5. 現在の実装範囲
Part 198では、移行準備チェック、方針表示、移行計画JSONの出力を実装する。実際の権限付与・解除は、クラウド認証APIに承認ワークフローを実装した段階で有効化する。


## Part 199 実装範囲

Part 199では、準備記録だけでなく、クラウドAPIとPostgreSQLを用いた段階移行ワークフローを追加した。

1. 有効な安全環境室長だけを候補として取得する。
2. MFA、メール確認、教育、並行運用、バックアップ、職制承認、監査確認を必須とする。
3. 現行管理者のパスワード再認証後、移行申請と切替予定日時を保存する。
4. 正式切替は環境変数 `ADMIN_SUCCESSION_ENABLED=true` の場合だけ実行する。
5. 切替後は安全環境室長の既存トークンを無効化し、管理者として再ログインさせる。
6. 旧管理者は移行支援期間中、管理者権限を維持する。
7. 切替後7日間は、理由と再認証を伴うロールバックを可能とする。
8. 申請、切替、ロールバックはすべて監査ログへ記録する。

正式移行前には、データベースと写真のバックアップ、復元試験、緊急復旧用管理者の保管、利用者への周知を完了させる。


## Part 200 移行後の完了管理

正式切替後は、安定稼働確認を記録し、支援期間終了後に移行先となった安全環境室長本人が移行完了を確定する。旧管理者の権限縮小は自動実行せず、利用者管理で変更した後、移行履歴へ確認結果を記録する。
