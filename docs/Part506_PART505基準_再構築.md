# Part 506（Part 505基準の再構築）

## 1. 再構築方針

本版は、Part 505の完全なシステム一式を基準に作り直し、後続版をそのまま継ぎ足していません。Part 505で確定した危険物、法令、包装要件、レスポンシブ表示等を維持した上で、今回必要な機能だけを再実装しています。

## 2. 申請番号管理との連携

申請書確認から登録する場合は、元申請書名、抽出した国連番号、品名、容器等級、容器コード、数量・質量、包装要件、許容容量・許容質量、警告、照会結果、確認者、確認日時を案件へ保存します。固縛力参考算出から登録する場合は、貨物質量、コンテナ番号、航路・条件、固縛・支保材、確認済み強度、強度根拠、方向別の必要抵抗力・現在抵抗力・余裕／不足、総合判定、警告、確認者、算出日時を保存します。

両方とも案件詳細で見やすいカードとして表示し、再登録時は第2版、第3版として履歴を残します。取消し後も監査履歴を保持します。

## 3. システム全体の本番環境移行

システム管理者の「システム設定」から、次を一つの移行単位として扱います。

- アプリケーション本体、HTML、CSS、JavaScript
- 危険物、国内法令、IMDG Code、包装要件、コード等の全マスター
- 法令原文、参考資料、画像等の静的ファイル
- 利用者、権限、所属事業所、運用設定
- 申請番号、メモ、更新・訂正履歴
- 申請書確認結果、固縛力参考算出結果
- 添付資料、関連写真
- 承認、原典照合、監査、訂正履歴
- バージョン情報、バックアップ・同期設定

移行は、事前診断、完全バックアップ、暗号化パッケージ作成、チェックサム検証、移行先ステージング、運用データ同期、移行先での確認、切替、ロールバックの順で行います。移行先へのステージングは稼働中の本番領域を直接上書きしません。

パスワード平文、MFA秘密鍵、APIトークン、セッションは移行しません。利用者は移行先で安全に再設定します。

## 4. 書体・色の全体見直し

業務画面は、BIZ UDPゴシック、Noto Sans JP、游ゴシックUI、游ゴシック、メイリオの順で使用します。法令引用は、游明朝、ヒラギノ明朝、Noto Serif JPの順で表示します。端末に先頭の書体がない場合も、日本語に適した代替書体へ自動的に切り替わります。

既存のSKロゴ、危険物標札、実寸表示、法定表示の形状・書体は変更していません。背景、本文、見出し、罫線、成功・注意・エラーの色を共通変数へ統一し、フォーカス表示とスマートフォンの操作領域も見直しました。

## 5. 本番配置時の条件

静的なGitHub Pagesだけでは、中央保存、サーバー側権限制御、自動バックアップ、移行先ステージングは動作しません。同梱のserverをPostgreSQLおよび永続ストレージへ接続し、SQL 094を含むデータベース移行を実施してください。

SYSTEM_MIGRATION_ENABLEDは初期値で無効です。移行作業時だけ有効にし、移行元オリジン、最大ファイル数、最大容量、ステージング先を環境変数で明示してください。
